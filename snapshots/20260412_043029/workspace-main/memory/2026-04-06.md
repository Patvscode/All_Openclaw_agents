### Root Cause Investigation (2 subagent runs, ~45 min total)

**Round 1 findings (30 min):**
- Ruled OUT InnerQ channel scaling as cause (it's disabled by default)
- turbo2 has NO InnerQ at all, yet still produces garbage → confirms InnerQ not the issue
- WHT rotation operates on 128-element groups — mathematically correct for any head_dim
- Suspected mismatched WHT sign arrays between encode and decode paths

**Round 2 findings (15 min):**
- Verified sign arrays in encode path (turbo-quant-cuda.cuh: `d_turbo_wht_signs1/2`) vs decode path (turbo-wht.cu: `d_turbo_wht_s1/2`)
- Verified KV cache tensor shapes for Gemma 4:
  - SWA layers: head_v=256, n_embd_v_gqa=256 (1 KV head)
  - Non-SWA layers: head_v=512, n_embd_v_gqa=512 (1 KV head for global attn)
  - All 128-aligned, no padding needed
- Set-rows processes 4 groups per 512-dim head — independent FWHT per group, mathematically fine
- Was writing a CUDA encode→decode round-trip test when session ended
- **No patch produced yet** — the bug is more subtle than array mismatches

### What This Means
1. The TQ fork's flash attention path is broken for Gemma 4 even with q8_0 (rotation issue) → fixed by LLAMA_ATTN_ROT_DISABLE=1
2. The turbo quantize→dequantize round-trip itself is broken for Gemma 4 → NOT fixed by disabling rotation
3. Both issues need fixes for TurboQuant to work on Gemma 4
